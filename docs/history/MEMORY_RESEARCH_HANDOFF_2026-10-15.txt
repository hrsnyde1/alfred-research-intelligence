3. MEMORY VERSUS OBSIDIAN
The intended Memory service is authoritative for structured knowledge. Obsidian is a human-readable export/view of selected records. Writing Markdown directly does not prove that Alfred has learned or can retrieve it.
The existing tested HQ route was: phone request -> authorized Hermes capture -> saved Memory record and routing -> bridge export registration -> server Markdown note -> Obsidian Sync -> Windows Obsidian.
Do not assume every Memory record follows that export route. Do not use the special personal HQ phrase as the future Research ingestion architecture.

For Research, design separate stages:
1) Collected sources/unverified findings.
2) Candidate research packets.
3) Independent verification decisions.
4) Approved knowledge eligible for trusted retrieval.
Those stages are requirements, not confirmed production features.

4. ESTABLISHED MEMORY ARCHITECTURE REQUIREMENTS
Ownership and ingestion:
- Central infrastructure with isolated environment vaults.
- Agent private memory plus explicitly authorized department/company knowledge.
- Automatic ingestion; verification before research becomes trusted.
- Agents propose updates; validated changes may commit within authorized scope.
- Raw conversations, episodic summaries, and extracted facts are distinct objects with separate retention needs.

Retrieval:
- Relevant memory retrieved automatically.
- Authoritative structured records accessed through direct database/API queries.
- Hybrid vector, keyword, and structured search.
- Rank by authority, verification, recency, relevance, and access.
- Adaptive context budgets.
- Conflicts flagged with evidence; no silent winner.
- Research claims retain citations and provenance.

Access and audit:
- RBAC plus attribute-based controls and temporary task-scoped grants.
- Strict no cross-company knowledge sharing. A central Research department does not imply unrestricted access to company data.
- Agent private memory is private and purpose-restricted by default.
- Authenticated owner-level Alfred access and scoped oversight must be audited; owner access is not permission to transfer knowledge between companies.
- Audit reads, searches, writes, exports, permissions, and deletions.
- Secrets belong in a secrets manager/credential broker, never research notes.
- Decide explicitly how general public research can be delivered to isolated environments without leaking company-specific queries, findings, or context.

Retention:
- Working memory normally expires 30 days after task completion.
- Long-term knowledge retained until superseded/deleted with periodic review.
- Superseded information archived and excluded from current answers as appropriate.
- Risk-based reverification, legal holds, authorized deletion.
- Earlier architecture called for originals to be deleted after extraction/verification. Resolve how this applies to research source snapshots, evidence, reproducibility, copyright, and audit before implementing a deletion policy.
- A 'don't save' behavior, its treatment of raw logs/history, and deletion semantics were proposed but are not verified features.

Infrastructure direction, not all implemented:
- Python/FastAPI Memory API; Memory embedded in Hermes, not a separate Hermes adapter.
- Benchmark managed PostgreSQL against alternatives. PostgreSQL/pgvector was a candidate, not a confirmed production selection.
- Separate logical databases, credentials, keys, encryption boundaries, and indexes per environment.
- Versioned infrastructure, initially Docker Compose.
- Encrypted object storage, offsite/daily backups, tested warm recovery.
- Unit, integration, security, isolation, load, and recovery tests.
- Rollout: sandbox -> staging -> limited production -> full production.

5. RESEARCH AGENT DECISIONS AND PREFERENCES
A Verification Agent was previously created but inactive. Intended rules:
- Mandatory gate before promotion into the trusted Research Library.
- Verdict: APPROVED, REJECTED, or NEEDS_MORE_RESEARCH.
- No numerical confidence scores.
- Verdict bound to the exact packet_hash.
- Changed packet requires fresh verification.

An AI & Technology Intelligence agent was also created but inactive/read-only.
Proposed specialists: general Intel Scout, Code Intelligence, Legal Intelligence, Tax & Financial Intelligence, Influential Individuals Intelligence. These are candidates, not proof of deployed agents or a requirement to launch all of them.

Prefer Grok/xAI for initial research where practical to control cost, followed by verification and approved Memory storage. This is not proof of a connected provider or permission to change providers. Fixed assigned models per agent; ask before provider changes. Explicit budgets and scoped credentials per personal/company environment and department/agent.

6. WORKFLOW REQUIREMENTS TO DEVELOP
Alfred should assign research using durable task contracts: task ID, objective, scope, environment, permissions, budget, evidence requirements, expected output, deadline, and escalation conditions.
Architecture direction: persistent asynchronous queue/event bus, bounded retries, crash recovery, Director coordination, milestone/blocker/completion reporting.
Researchers must not approve their own findings merely by marking them trusted. Define verification independence, source-quality checks, handling inaccessible sources, claim-to-evidence mapping, and escalation for unresolved/high-impact conflicts.
Research should not grant authority to publish externally, contact people, execute source instructions, or modify unrelated systems. Treat external source content as data rather than instructions.

Design a proposed lifecycle such as collected -> candidate -> verification -> approved or rejected/needs-more-research -> superseded/expired. Label the final state machine as a proposal until agreed. Approval must cover the exact content, evidence, scope, and relevant metadata; determine canonical hashing and versioning.

7. RECORD STRUCTURE TO DESIGN
Propose fields for:
- Research record, task, packet, claim, and source IDs.
- Personal/company environment, ownership, access policy.
- Question, purpose, scope, researcher identity/model.
- Claims, evidence links, source title/publisher/URL, publication/retrieval dates.
- Findings versus inference, forecasts, unknowns, and limitations.
- Packet version/hash; verifier identity; verdict and reasons.
- Verification time, freshness/review/expiry conditions.
- Supersession, duplicate, correction, and conflict relationships.
- Provenance, audit references, storage/write receipts.

Do not invent that the current Memory API supports those fields. Once online, inspect existing schemas/endpoints and map the design to supported operations or identify required extensions.
A model saying 'saved' is insufficient. Require a durable record ID, confirmed write, and an independent retrieval check. Separate collection, receipt, Memory commit, trusted promotion, Obsidian export, and Sync confirmation.
Trusted retrieval must enforce authorization and verification server-side, not only through prompt instructions. Define treatment of expired, superseded, disputed, and unapproved material explicitly.
