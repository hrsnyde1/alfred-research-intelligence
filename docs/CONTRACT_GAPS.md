Source outcomes: `SUPPORTED_FETCHED`, `PARTIAL`, `AUTH_REQUIRED`, `INACCESSIBLE`, `UNSUPPORTED`, `ERROR`. Partial fetch never implies full viewing/transcription. One submitted source may have internal files/child skills. Independent corroboration, when warranted, attaches supporting evidence to the same task; it must not become unsolicited discovery or a second user-source task. Define permitted corroboration and budget limits before live fetch.

## Required compatibility decisions

1. **Identity:** host-issued tenant IDs and authenticated principals are authoritative. Reject unknown/ambiguous mappings rather than infer tenant from URL, company name in text or model output. Public source classification does not authorize copying company-specific questions/context.
2. **Verification:** specify verifier registration, role separation, canonical JSON rules, evidence digest coverage, policy-version changes and approval invalidation. Memory must validate authority and exact scope, not merely accept an APPROVED string.
3. **Promotion:** determine whether Memory can atomically validate decision and promote, or needs separate candidate/commit/promote calls. A write receipt does not establish trusted retrieval; fresh authorized read-back is mandatory.
4. **Idempotency:** determine key scope, dedupe retention, timeout reconciliation, version preconditions and receipt lookup. Target exactly-once effects through idempotent operations, not an unsupported exactly-once transport promise.
5. **Distribution:** confirm existing specialist profile identifiers and server-side authorization. Development categories are Frontend, Backend, Full-Stack, DevOps, Data Engineering, Data Science, AI/ML, Integration, Security, Mobile and Performance. Matching does not create agents or grants.
6. **Retention:** Memory reference suggests working memory expiry 30 days after completion and long-term retention until superseded/deleted. Snapshot-original deletion conflicts with reproducible verification; agree evidence retention, legal hold, deletion and audit policy before automatic cleanup. Do not silently implement the proposed “don't save” behavior.
7. **HQ:** eligibility is distinct from access. Owner reads must be audited and partition-preserving; company agents never inherit owner authority. Define revocation/delete propagation before enabling sync.
8. **Notifications:** define required completion stages and partial status. “Analyzed; Memory unavailable” is different from “saved and available.” Message acceptance is different from confirmed delivery. Avoid source payload or secrets in short messages.

## Phase 1 corrections — persistence and replay contracts

- Corrected local persistence is schema v2, with immutable packet revisions, a current-head pointer, exact task/version/digest/environment decision links and immutable retry-operation results. Internal packet/request/verdict wire schemas remain v1. No Linux schema compatibility is implied.
- Existing v1 files are deliberately unsupported and rejected without modification. No automatic migration/import or data deletion is implemented. Any future import must be separately reviewed and cannot recover historical content already overwritten by the previous implementation. Compatible v2 files are validated without DDL and retain their state.
- Existing-file validation uses a read-only SQLite preflight and an exact schema manifest, followed by validation under the application transaction lock. Additional/missing schema objects fail closed; future indexes or schema extensions require an explicit version/migration decision.
- New-file publication uses fully initialized private same-directory staging and a no-overwrite hard link. Confirm Linux filesystem support and durability/backup behavior before deployment; this is separate from existing Memory/Obsidian staging and does not modify it.
- Callers must persist a logical retry ID and pass it to `retry(context, task_id, retry_id)`. It is bound to environment/task/requesting principal. Replay returns the original committed result, not necessarily the latest task state; use `get_task` for current state. Host dispatch/replay IDs must map deterministically to these local operation IDs.
- `get_packet`, `packet_history`, `verification_history` and `get_retry` provide authenticated environment-scoped historical reads. These are internal library operations, not new host APIs or Memory retrieval endpoints.
- Retry replay does not append audit/outbox effects. Future external delivery still needs its own attempt IDs and receipt reconciliation; the existing local delivery-status primitive is not an exactly-once transport implementation.


## Recovery authorization correction — independent test authority

- Untrusted receipt JSON is no longer proof of registration. Persistence requires an explicitly injected OfflineRegistrationAuthority with a live active ledger record. Registration binds canonical intended path, environment, schema/manifest, device/inode, random authority and registration IDs, current environment epoch and registering principal. Receipt editing/copying/replay cannot update this independent ledger.
- This authority is strictly an in-memory offline test provider (`test_only=True` required). Production Store/open/register paths are disabled. There are no cryptographic keys, real credentials or additional services. Linux must provide a protected, durable, independently trusted authority before production can be enabled; do not deserialize user/DB/receipt/model content as authority state.
- Only authorized provisioning of a genuinely new Research database registers implicitly. Existing compatible files require the explicit issued-director `register_database` operation; replacement must be explicit. Cold schema validation must complete before any new registration. Unknown hot files cannot be registered to bypass SQLite recovery authorization.
- Revocation and epoch rotation are director-authorized and environment scoped. Replacement and rotation invalidate previous receipt replay. Loss/change of injected trust material denies recovery. Test workers receive current authority state through trusted harness stdin, not a sidecar or user input. This is not a production backup or registry-import implementation.
- Backup/restore and authority key lifecycle remain integration gaps. Production restoration must preserve current revocation/epoch state or start a new authority generation with explicit validated registration; stale snapshots must not silently restore eligibility. Missing or ambiguous authority state must fail closed. No automatic schema/receipt-only migration is provided.
- For an independently authorized registered file, SQLite may need to recover before its current schema can be known. Post-recovery incompatibility remains an explicit RecoveryValidationError reporting possible physical mutation, with no schema migration or application operation. Unknown/forged/revoked registrations fail before writable opening.
- Path/device/inode identity is an offline binding, not a claimed defense against hostile same-account filesystem mutation or inode reuse. Protected grants, registry availability, cross-process authority concurrency, filesystem ownership, anti-rollback restoration, power-loss durability and real Linux authorization remain unverified. No Memory/Hermes/Photon/Development interface is replaced.

- Local directory inspection is authorized only within trusted, non-overlapping environment fixture roots. No file persistence/temp staging is introduced; evidence retention, snapshot storage, atomic publication, deletion/licensing and audit need separate reviewed ownership before implementation.
- Parser limits enforce input/file/output/work ceilings and a cooperative deadline per operation. Agree hard worker CPU/RSS enforcement, concurrent per-environment quotas and authoritative provider receipts before live execution. Production source processing remains disabled.
- GitHub needs authorized read-only provider/Git object access, resolved commit/tree verification and bounded acquisition; submodule/network dependencies are flags, never fetched. JSON manifests are inspected; YAML/TOML and dependency declarations remain text with limitations, not a complete semantic or vulnerability analysis. - YouTube/Instagram/TikTok/X process fixture or user-supplied text only. Metadata-only or unavailable media cannot be marked watched/transcribed. Fixture dates/access outcomes must never be rebranded as real provider evidence.

Host retries may reprocess deterministically, but durable snapshot storage would require its own explicit version/idempotency/retention contract. No Memory, Photon, Hermes, CTO or Development interface was modified.
