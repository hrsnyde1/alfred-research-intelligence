## 4. Rollback prerequisites and procedure to approve

Before staging/production, record exact existing code/config hashes and installed entrypoints, service state, permissions, backup/restore proof, current revocation/registration generations and pending operation/receipt inventory. A waiting backup timer or rollback-named directory proves neither restoration nor anti-rollback. Define backup scope/retention with Memory/Security owners without copying live data into this repository.

Under a later explicit rollback authorization: disable only newly introduced Research dispatch/attachment and preserve pending work; reconcile external operation/message results before resending; return routing/configuration to the inspected approved baseline; retain immutable task/evidence/verdict/proposal/receipt history and current revocations. Select a prior code release only if schema/authority compatible. Quarantine incompatible Research state for reviewed recovery instead of resetting it or silently migrating it.

Do not restart/stop existing Hermes/Photon/Memory/Obsidian/Development as an assumed rollback step; any needed service action must be separately approved. Never restore stale registration/credential epochs, reverse published Memory/HQ/Obsidian state blindly, discard deletion tombstones, delete databases or alter existing Development approvals. Already published knowledge may need a Memory-owned compensating correction/revocation, and delivered misinformation a separately authorized correction message.
